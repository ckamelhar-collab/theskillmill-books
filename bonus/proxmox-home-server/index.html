1. Hardware sizing worksheet (Chapter 3)

Fill in the right-hand column before you buy anything. The book’s rule: spend on memory, not cores.

  • Processor: anything from the last decade with virtualization support (Intel VT-x / AMD-V). Enabled in BIOS? ______ (it frequently ships disabled)
  • Cores: 4 runs a dozen light services. Cores I actually need: ______
  • Memory: 8 GB frustrates within a month, 16 GB is the working minimum, 32 GB is where you stop thinking about it. Planned: ______ GB
  • ZFS? If yes, it takes up to half of RAM for its cache, so add memory rather than counting on it. Adjusted: ______ GB
  • System and guest disk: SSD, never a mechanical drive. Check the endurance rating; avoid no-name drives. Model: ______
  • Bulk storage: spinning disks only for media and files. Mirrored? ______
  • Idle power: a mini PC idles near 10 W; an auction rack server can draw 100 W+ (roughly 10x the yearly running cost). Estimate: ______ W
  • Which build am I buying? Cheap experiment (used mini PC, 16 GB, 500 GB SSD, about $120–200) / Comfortable (32 GB, 1 TB SSD, about $350–500) / The one that grows (tower, 32–64 GB, SSD + 2 mirrored disks, about $600–900)

Before the first boot, in BIOS: enable virtualization; enable IOMMU (VT-d / AMD-Vi) if you will ever pass hardware through; set “Restore on AC Power Loss” to on. In the installer: open the Options button and choose the filesystem deliberately (changing it later means reinstalling); give the machine a static IP outside your router’s automatic range; put a real email in the email field so failed backups can reach you. Write the IP and the root password down somewhere real.

2. Container or virtual machine? (Chapter 6)

Default to a container. Reach for a VM only when one of these is true.

  • Needs a non-Linux OS (Windows, a BSD, anything with its own kernel) → VM
  • Needs kernel modules, some VPNs, certain filesystem tools → VM
  • Exposed directly to the internet and wants the stronger isolation → VM
  • Shipped as a complete VM image (Home Assistant’s own image, for example) → VM
  • Following a guide written for a VM and not ready to translate it → VM, and that is fine while learning
  • Everything else → container (starts in 1–2 s, uses only the memory it needs, roughly 4x the useful capacity from the same box)

Starting allocations (assign less than you think; raising is easy, reclaiming means a shutdown): light container 1 core / 512 MB / 4–8 GB disk · heavier container such as a media server 2 cores / 2 GB · general Linux VM 2 cores / 4 GB / 32 GB · Windows VM 4 cores / 8 GB / 64 GB minimum.

Unprivileged by default. Choose privileged only when you can say exactly why, and never for anything reachable from the internet. A tutorial that “fails for you and works for everyone in the comments” usually assumed a privileged container without saying so.

Name every guest for its job (pihole, plex, backup-target), use the Notes field, keep an address list, set start order with DNS first, and delete dead guests.

3. Backup tier checklist (Chapter 10)

Sort every guest into one tier. Do not give all three the same schedule.

  • Tier 1 — cannot be recreated (photos, documents, password vault, notes): frequent backups, several retained copies, at least one copy somewhere else physically. Guests: __________
  • Tier 2 — tedious to rebuild (Home Assistant with its automations, the media server’s libraries): weekly, a few copies kept. Guests: __________
  • Tier 3 — recreatable in an hour (test containers, experiments): no backup; exclude them. Guests: __________
  • Mode: snapshot for nearly everything. Retention: several dailies plus a few weeklies — a single copy backs up the corruption. Location: a copy is only a backup when it is somewhere else.
  • Bulk media: back up the server’s configuration, let the films be replaceable.
  • Notification email configured? ______ A failing job that emails nobody is the same as no backup.
  • Restore drill: restore one guest as a new ID, start it, confirm, delete. Done on ______ (repeat every ~6 months and after any storage change).
  • Monthly: open the backup storage and look at the actual files and sizes.
  • Restore procedure written on one page, kept OFF the server? ______ Host config copied off the machine? ______

4. The six-check diagnostic card (Chapter 12)

Work these in order before searching any error message. About ten minutes.

  1. Is the host up? Web interface loads? Ping answers? If not, it is the machine or the network — nothing below matters yet.
  2. Is any storage full? A full disk causes an extraordinary range of unrelated-looking failures. Check every storage on the node summary.
  3. Is the guest actually running? A guest that failed to start after a reboot looks exactly like a broken service.
  4. What does the guest’s console say? Open the Console tab, not a network connection. Boot errors and failed services show here even when networking broke.
  5. Network or service? From the console, reach something outside. Cannot → network (address, gateway, bridge). Can, but you cannot reach the service → the service is down.
  6. What changed? An update, a config edit, a power cut, a disk filling. Check your notes and incident log; a snapshot taken before the change pays for itself here.

Discipline: write the symptom down before touching anything; change one thing at a time. Stop rule: decide now how long you will repair before you restore — 2 hours is reasonable. My number: ______ Write it next to the restore procedure.

Quick lookups: “KVM” in a VM start error = virtualization off in BIOS · guest will not start with free memory = look at what is assigned, not used · everything slow at once = storage full, or a backup / ZFS scrub running · container cannot read a mounted folder = unprivileged mapping (Chapter 6) · “running” but nothing responds = the service inside died, open the console · updates fail with an auth error = enterprise repo without a subscription (Chapter 2) · USB device vanished after moving a cable = attached by ID, re-attach by port.
